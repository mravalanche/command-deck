# Command Deck — design language

**Current design:** The application uses Midnight Ink without a theme switcher. Midnight Violet remains an alternate in the standalone design showcase. IBM Plex Sans is the interface font, while CaskaydiaCove Nerd Font is used for short technical labels and unavailable-telemetry messages. All dashboard data in the previews is illustrative.

## Typography

- **IBM Plex Sans:** body, controls, navigation, status and large values. Use 400 for prose, 600 for labels, 700 for major headings and values.
- **CaskaydiaCove Nerd Font:** hostnames, paths, units and short technical labels. Do not rely on a font glyph alone for critical status.
- Start with 16 px body labels, 19–21 px values, 26–28 px top status and 13–14 px secondary context. Card update ages can be 11–12 px because they are supplementary.
- Use tabular numerals for changing values and capacity pairs. Application fonts and licenses are bundled locally.

## Dashboard patterns

The target display sizes are 800 × 480 and 1024 × 600; confirm the physical panel later. The Overview is glanceable, with more detail in Servers and Events.

- **Telemetry label:** a subtle dot and word: CONNECTED, UNHEALTHY or DISCONNECTED. This is about data freshness and source quality, not the monitored system's health.
- **Server card:** neutral left rail while telemetry is connected. A specific capacity concern appears on its storage row and in Attention. A disconnected server has a red rail and “Telemetry unavailable” instead of stale values.
- **Backup card:** green rail when scheduled jobs are on time; red when a job is missed or failed. The telemetry label separately reports whether Healthchecks data is trustworthy.
- **Availability card:** a count such as 11 / 12 is neutral information. A missing service is elevated only if its importance or an existing alert warrants it. Unhealthy telemetry has an amber rail; disconnection has a red rail.
- **Freshness:** each card has a subdued relative update age in its bottom right. The date and seconds clock in the upper right use the display device's local time. Production freshness will come from actual collector timestamps.
- **Navigation and controls:** at least 44 px touch targets, visible keyboard focus, no unnecessary animation. The chosen CPU and memory treatment is split numbers with a quiet divider.
- **Status model:** OK, WARNING, CRITICAL and UNKNOWN for monitored conditions. Unknown or stale data must not appear healthy. Source health is separate.

### Servers view direction

- Show one selected host's detail at a time. The host selector follows config file order.
- With a few hosts, use equal-width host buttons and no arrows. With many hosts, use a horizontally scrollable strip, aligned arrow controls, and visible selection. Keep host buttons at least 44 px high.
- The selected host shows split CPU/memory numbers, compact storage bars, and a five-minute CPU and memory trend with a legend. The [Servers preview](design/servers-preview.html) has three-host and eight-host examples; all values are illustrative.
- Fetch the selected host's trend from Prometheus `query_range` when selected. Cache the response briefly; do not store a second time series in the app. If history is incomplete, label the available window honestly.

## Component selection

| Pattern | App use |
| --- | --- |
| Attention strip, server card, split CPU/memory values, compact storage row, telemetry dot and word, relative update age | Canonical Overview and Servers patterns. Phase 2 starts with Prometheus data. |
| Backup and availability summary cards | Canonical Overview patterns. Show UNKNOWN until their collectors are connected in Phase 3; never use the showcase's sample values as live data. |
| Current signal row with severity, reason, source and data age | Canonical Events pattern until a verified event feed can supply failure and recovery times. |
| DaisyUI buttons, inputs, selects, loading indicator and skeleton | Shared controls and HTMX loading states. Use the same focus and touch sizing throughout. |
| DaisyUI table and disclosure | Detail views only, where extra rows and explanations are useful. Keep Overview compact. |
| DaisyUI alert | Inline errors or confirmations in detail views. The custom Attention strip remains the dashboard's problem summary. |
| DaisyUI badges, stats, steps and static tab example | Gallery reference only. Health and telemetry keep their established labels and rail treatment. |

The showcase dialog demonstrates styling but is not needed for the initial Overview. Add it when a specific interaction requires a modal. The three main views use the established navigation instead of DaisyUI tabs.
